# SPL testing and verification strategy

26 November 2026. The owner selected **authored Readable SPL as the starting
point of the correctness proof**. The future tool should certify each
compiled contract and check that certificate when the contract runs.
Traditional tests help people understand the financial implications of
authored SPL and check how the deployed tool behaves in its actual
environment.

## Certify the translation from Readable SPL

For each supported compiled contract, the intended certificate establishes
that the actual emitted Lean settlement preserves the meaning of the
authored Readable SPL for every admissible input and opening state. The
statement names the language version, linked policy definitions, admitted
domain and observations. The intended observations include exact amounts,
rounding, financial failures, selected decisions, closing state and the
promised audit information. The proof may pass through typed core as an
intermediate step. It must cover the step from the authored source through
parsing, readable expansion, binding and elaboration.

For example, an expansion could turn “sum, then round” into “round each
line, then sum.” A correct typed-core lowering could faithfully implement
the altered rule. The certificate therefore needs a meaning for Readable
SPL defined independently of the expansion under test. Its statement must
bind the exact source, linked policy and emitted Lean artifact, with an
independently controlled checker enforcing the statement and its assumptions.
A compiler update can produce new certificates under the same approved
semantics. Rechecking an artifact certifies that translation. Acceptance,
termination of compilation and ability to produce a certificate on the
supported corpus are separate properties.

One certificate can cover future periods for the same artifact. Each run
must establish that it is using the certified artifact and that the actual
input and opening state satisfy the stated assumptions. Changed source,
policy or artifact identity requires renewed certification for the changed
translation. If the proof ends at Lean semantics, the connection to the
native executable and its environment remains an explicit obligation.
Mathematical verification applies wherever we can specify that connection
and check the assumptions it relies on. [Compiler correctness scope](core-and-compilation.md#10-correctness-claims-and-trusted-boundary) ·
[Translation Validation](https://doi.org/10.1007/BFb0054170)

## Verify the input and output boundaries

Each runnable contract should have explicit, versioned input rules. A
linked definition file is one possible format. The writer agent can draft
it and explain the checks in readable terms. Relevant rules include input
types and units, unique original identities, approved recipients,
allocation conservation, coverage against a supplied population, and
opening state tied to a completed predecessor. Rules should be traceable
to agreed requirements or explicit assumptions.

The proposed proof obligation is that successful admission establishes the
declared preconditions for the settlement. A related boundary property is
that invalid input, a preview, or a failed publication cannot expose
consumable closing state when the profile disallows it. Consider proving
these properties over the validator and publication model, with a checked
connection to the implementation. The parties and their evidence establish
whether the chosen requirements are sufficient and whether the real-world
records are complete. A completeness check against a supplied roster
establishes coverage relative to that roster.

The compiler can hide implementation details such as how it performs a
join. The writer should be able to see choices that affect money, recipients,
dates, state or audit results. A useful invariant says that split
contributions sum to their original receipt. The proof should also preserve
the approved recipients, since two differently attributed results can both
conserve the total. [Input and run contract](data-and-run-contract.md) ·
[Publication contract](artifact-publication-design.md)

## Tests that help people review a contract

The writer agent should show the proposed Readable SPL, the clause or
instruction behind each material choice, any unresolved alternatives, and
worked examples that distinguish those alternatives. Participants can then
review consequences in amounts, recipients, timing and successor state.
Use independent expectations derived from original facts or agreed worked
examples. An expected answer generated by the same translation can repeat
its interpretation error.

For example, two one-cent lines at a 50% share distinguish half-even
rounding per line from half-even rounding after aggregation. The first
method yields USD 0.00 and the second USD 0.01. A compiler can correctly
implement either approved rule. A worked example helps a human tell which
rule the SPL will apply. Use similar examples for a disputed crossing
event, a missing validation rule, or the next close after a state change
when those differences matter to the deal. Test the writer tool's ability
to expose those choices and show the consequence of each.

## Integration and QA for the deployed tool

Run representative checks through the actual writer, certification,
execution and public consumption paths as those parts become available.
Most of these checks can be shared across contracts.

| Scenario | Expected behavior |
| --- | --- |
| A certificate is missing, stale, or bound to a different source, policy or executable | The tool refuses the run and identifies the mismatch. |
| Publication stops between writing closing state and committing the result | A restart and public reload cannot consume the incomplete state. A successful successor uses the exact preceding completed result. |
| A runtime exceeds a resource bound | The tool reports the failure and exposes no consumable closing state. Measure capacity on the deployed path under its stated assumptions. |
| A user reviews a preview or blocked run | The displayed status, available artifacts and public reader agree on which results can be used. |
| A compiler, language or schema update reaches existing contracts | Check that supported contracts still compile and certify. Prove preservation of old-version meaning where claimed. Exercise old packages, policy links and saved state across affected operational boundaries. |

A protocol proof can cover more of these behaviors as its model and
implementation connection mature. Keep deployment tests where the proof
assumes properties of files, processes, the executable chain, configuration
or the interface a person sees.

## How the suite changes as proofs expand

Review existing tests at the level of individual assertions. One contract
case can contain an independent financial example, interpreter and emitter
agreement, and a public reload check. A Readable SPL certificate can take
over the translation claim while the example and reload continue to protect
their own claims. Keep the baseline regressions during the transition.
Reduce combinations and repeated lowering checks when checked proofs cover
the same property across the relevant domain and the shipped path uses that
proof. Keep targeted regressions for remaining assumptions, verifier
rejection, compatibility and operational failures.

For a compiler change, identify the changed promise and its proof boundary.
Re-certify changed translations. Add a traditional test when it exercises
a named behavior or assumption that the checked proofs leave open.
